# Выпуск версии

Порядок выпуска целиком выполняет `scripts\publish-release.ps1`. Раньше он существовал только как
настройка рабочей копии (`remote.origin.push = publish:refs/heads/main`) и терялся при переносе на
другой компьютер; теперь он записан в скрипте, и его шаги проверяемы.

```powershell
# 1. Поднять <Version> в Directory.Build.props и закоммитить (в сообщении коммита — версия в скобках).
# 2. Собрать нативные библиотеки AnyConnect, если каталог third_party\openconnect\bin пуст
#    (их хеши должны совпасть с binaries в third_party\openconnect\manifest.json).
#    Скачать движок "VPN поверх SSH" и архив его исходников (хеши сверяются с third_party\sing-box\manifest.json):
#    scripts\fetch-sing-box.ps1
# 3. Выпустить:
scripts\publish-release.ps1 -NotesFile docs\notes-0.8.0.md
```

Что делает скрипт:

1. **Проверки.** Корень репозитория и каталог git (в git worktree — общий каталог основной копии) не доступны
   на запись Everyone, Authenticated Users и Users (см. [ниже](#права-на-рабочее-дерево)). Версия совпадает с `Directory.Build.props`, рабочее дерево чистое, тега ещё нет,
   `gh` авторизован, файл заметок и ключ подписи на месте. Файл вне git среди входов сборки (`src\`,
   `tests\`, `installer\`, `Directory.*`, `global.json`, `nuget.config`) — ошибка выпуска, в том числе
   скрытый `.gitignore` (`*.csproj.user`, `*.dll`): он попал бы в MSI, но не в снимок исходников. Каталоги
   вывода `bin`, `obj`, `TestResults` не в счёт.
2. **Сборка и испытания.** `dotnet build SplitVpn.slnx -c Release` без предупреждений и полный набор тестов текущего решения через `dotnet test SplitVpn.slnx -c Release --no-build`. Установщик в решение не
   входит и собирается только на следующем шаге. Аудит уязвимостей пакетов NuGet включён; без доступа к
   api.nuget.org (ошибка `NU1900`) — `-OfflineNuGet`, с предупреждением о пропущенной проверке.
3. **Установщик.** `scripts\build-installer.ps1 -Version <версия>`: DLL AnyConnect сверяются с SHA-256 в
   отслеживаемом `third_party\openconnect\manifest.json` (`binaries`). Затем `ProductVersion` внутри MSI
   и версия файла `SplitVpn.Service.exe` в его таблице File сверяются с выпускаемой версией — это ловит
   «выложили пакет от прошлой сборки» и MSI, собранный с новой версией поверх старой публикации.
4. **Манифест `update.json` и подпись к нему.** Манифест собирается строкой с фиксированным порядком
   полей и пишется как UTF-8 без BOM с переводами строк LF: подпись считается по точным байтам файла,
   поэтому он никогда не пересериализуется. Подписывает и тут же проверяет `splitvpn-cli`— тем же
   кодом, что и служба, так что разойтись форматы не могут. Утилита не ищется в `bin\Release`: скрипт
   публикует её из текущего дерева в очищенный `artifacts\release-tools` (и при `-SkipBuild`), сверяет
   версию файла с выпускаемой и вызывает только оттуда.
5. **Снимок исходников.** Один коммит без истории в локальную ветку `publish`. Приватная история `main`
   не публикуется: в ней остаются адреса серверов и внутренние имена. Манифест добавляется только во
   временный индекс снимка — рабочее дерево и история не меняются.
6. **Релиз.** Тег `v<версия>` отправляется на снимок, затем `gh release create v<версия> --verify-tag`
   с тремя активами: MSI, `update.json`, `update.json.sig`. В заметки дописываются SHA-256 установщика и
   предупреждение об отсутствии подписи Authenticode. Не создался релиз — скрипт удаляет тег и черновик,
   `main` не меняется.
7. **Снимок в `main`.** `push --force-with-lease` снимка в `main` на GitHub — только после релиза: из
   `main` манифест раздают зеркала jsDelivr и raw.githubusercontent, и он не должен ссылаться на
   установщик, которого ещё нет. Если отправка не прошла, релиз уже выложен, а зеркала отдают прежний
   манифест; команду повтора скрипт печатает.
8. **Проверка выложенного.** Манифест скачивается обратно по адресу последнего выпуска, проверяется
   подпись, сверяются версия и размер установщика.

`-DryRun` доводит дело до снимка и не отправляет ничего наружу. `-SkipBuild` берёт уже собранный MSI
(проверки версии из шага 3 действуют и для него); утилита подписи публикуется и в этом случае.

## Права на рабочее дерево

Скрипты выпуска и разработки исполняют код из дерева от администратора или SYSTEM, а выпуск
подписывается ключом. Если в дерево может писать любой пользователь компьютера, он подменит скрипт
или исходник без прав выпускающего. Корень диска (`D:\`) по умолчанию даёт Authenticated Users
«Изменение», и каталог, созданный в нём, это наследует. Права проверяются по SID (Everyone
`S-1-1-0`, Authenticated Users `S-1-5-11`, Users `S-1-5-32-545`): `publish-release.ps1` такое дерево
не выпускает (осознанный обход — `-AllowWritableTree`), `build-installer.ps1`, `elevated.ps1` и
`install-dev-service.ps1` предупреждают. Сами скрипты права не меняют. Исправить (консоль
администратора, `<SID>` — ваш SID, `whoami /user`; точную команду печатает `publish-release.ps1`):

```powershell
icacls D:\VPN /inheritance:r /grant:r "*<SID>:(OI)(CI)F" "*S-1-5-18:(OI)(CI)F" "*S-1-5-32-544:(OI)(CI)F"
```

Правило, заданное на корне явно (не унаследованное), снимается отдельно: `icacls D:\VPN /remove:g *S-1-5-11`.

Проверяется не только корень рабочего дерева, но и каталог git: `git rev-parse --git-common-dir` и
`--git-dir` (с их `hooks`, `config`, `config.worktree`) и каталог `core.hooksPath`, если он задан. Git
исполняет оттуда код при каждой команде — hooks, `core.fsmonitor`, `core.hooksPath`. В **git worktree**
(например, `D:\VPN\.claude\worktrees\<имя>`) общий каталог git лежит вне рабочего дерева — в основной
копии (`D:\VPN\.git`), — и закрыть права на одном каталоге worktree мало. `publish-release.ps1` печатает
команды `icacls` для каждого проблемного пути; для файла (`config`) — без `(OI)(CI)`.

## Ключ подписи выпусков

Установщик не подписан Authenticode, поэтому подлинность обновления держится на подписи манифеста:
скачанному по HTTPS доверять нельзя — подложный корневой сертификат в хранилище машины делает
перехват незаметным, а программа рассчитана на работу под блокировками.

- Алгоритм — ECDSA P-256 / SHA-256, формат подписи **IEEE P1363** (64 байта), задан явно и в
  `UpdateManifestVerifier`, и в команде подписи.
- Закрытый ключ — зашифрованный PKCS#8 в `%USERPROFILE%\.splitvpn\release-signing.pem`.
  Пароль хранится в `release-signing.password.dpapi` (DPAPI текущего пользователя); если файла
  нет, `publish-release.ps1` спрашивает пароль. Заданную `SPLITVPN_SIGNING_KEY_PASSWORD` скрипт при
  запуске переносит в SecureString и удаляет из окружения (и из сеанса, откуда запущен): сборка и
  тесты её не видят, утилите подписи она выставляется только на время подписи. Открытый текстовый файл пароля не использовать:
  перевести старый `release-signing.password.txt` — `scripts\protect-signing-password.ps1 -RemovePlainText`.
  **Сделайте копию ключа и отдельно запишите пароль вне этого компьютера** (файл `.dpapi` на другом
  ПК не расшифруется). Без ключа ни одна установленная копия программы не примет новый выпуск.
- Манифест подписывается вместе со сроком годности `expiresUtc` (по умолчанию +60 суток,
  `-ManifestLifetimeDays` 7–365). Для версий новее 0.9.5 срок обязателен; просроченный манифест
  клиенты считают «новых версий нет». Если выпусков долго нет, манифест нужно перевыпустить.
- Открытый ключ зашит в `src\SplitVpn.Core\Update\UpdateTrust.cs` — словарём по идентификатору
  `kid` из манифеста.

Создать новый ключ:

```powershell
splitvpn-cli release-keygen --out %USERPROFILE%\.splitvpn\release-signing.pem --kid sv-2027-01
```

Команда печатает строку для `UpdateTrust.PublicKeys`.

**Смена ключа** идёт через промежуточную версию: сначала выпускается версия, знающая и старый, и
новый ключ (оба в словаре), подписанная **старым**; после того как пользователи на неё обновятся,
следующий выпуск подписывается новым, а старый убирается из словаря. Если выбросить старый ключ
сразу, обновление не примут те, кто ещё не поставил промежуточную версию.

## Заметки к выпуску

На русском, обязательно: что нового, состав и протоколы, требование закрыть `SplitVpn.exe` перед
установкой поверх, команда `msiexec`. SHA-256 и предупреждение о неподписанном установщике скрипт
дописывает сам — в файле заметок их дублировать не нужно.

**Первый абзац файла заметок идёт в манифест** и показывается в карточке «О программе» перед
установкой: напишите его как короткую сводку выпуска (до 600 знаков). Остальной текст уходит только
на страницу выпуска. Файл читается как UTF-8 независимо от наличия BOM.

## Почему не GitHub Actions

Сборка MSI требует нативных библиотек AnyConnect, которых в git нет: их собирает
`scripts\build-openconnect.sh` под MSYS2 из закреплённых по SHA-256 исходников и пакетов. На чистом
раннере это десятки минут на каждый прогон, а версии пакетов pacman со временем уезжают — сборка
начнёт падать на каждом выпуске, пока хеши не обновят вручную. Кроме того, закрытый ключ подписи
пришлось бы хранить секретом репозитория: тогда компрометация учётной записи GitHub давала бы и
право выложить релиз, и ключ, которым он подписан, — то есть обесценивала бы саму подпись.
Локальная сборка уже настроена и воспроизводима по хешам.

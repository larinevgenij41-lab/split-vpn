# Проверка ресурсов и сбоев — 2026-09-24

Продолжение оптимизации поверх `24039c7`, рабочие изменения в `D:\VPN`, ветка `main`.
Проверены обработчики DNS, IPC, очередь координатора, доменные закрепления и завершение AnyConnect.
Первый проход: пять проблем воспроизведены тестами до исправлений. Второй проход описан в пунктах 6–11,
третий — в пунктах 12–17, четвёртый — в пунктах 18–24. В четвёртом проходе 12 новых случаев
сначала воспроизвели ошибки; ещё три проверяют сохранение нужного поведения после исправлений.

## 1. Общий IP двух доменных правил менял путь уже выданного адреса

`Coordinator.ObservePinnedAsync` заменял запись по IP без проверки действующей цели. Например,
ответ для `private.example → VPN` закреплял IP за туннелем, а затем ответ для
`public.example → напрямую` перенаправлял тот же IP напрямую. Оба ожидающих клиента могли
получить подтверждение, хотя первый маршрут уже был заменён.

Теперь весь DNS-ответ проверяется под блокировкой до изменения записей. Если хоть один IP
имеет живое закрепление за другой целью, ответ отклоняется целиком; посредник возвращает
SERVFAIL. Существующая цель сохраняется. После истечения TTL IP можно назначить другой цели.
Отклонение не оставляет частично добавленных адресов.

Тесты `CoordinatorPinConflictTests`: конфликт после применения и до первого применения,
отсутствие частичной записи, запрет прямого маршрута, повторное назначение после TTL.
Проверена политика и действия на подменённых системных операциях; реальная утечка трафика
через установленную службу не воспроизводилась.

## 2. DNS-посредник освобождал ресурсы раньше принятых запросов

`DisposeAsync` ждал только циклы приёма, но не созданные ими задачи UDP/TCP. Обработчик мог
продолжить работу и вызвать `Release` уже освобождённого семафора. Завершение службы также
не означало, что клиентские сокеты уже закрыты.

Добавлен учёт только незавершённых обработчиков; завершённые задачи удаляются из набора.
Остановка отменяет приём, дожидается обработчиков и upstream-запросов и затем освобождает
общие ресурсы. Повторное освобождение безопасно; повторный запуск не теряет старый сокет.
Сокет освобождается сразу и при неудачном Bind.

`DnsShutdownTests` проверяет остановку с работающим UDP/TCP-обработчиком и 25 циклов
запуска/остановки. После каждого цикла оба порта успешно занимаются новыми сокетами без GC.
Тесты используют случайные порты loopback, не системный порт 53.

## 3. Отмена IPC сохраняла канал с незавершённым обменом

После отмены чтения канал оставался открытым. В отличие от таймаута, отмена пользователем
не обрабатывалась `ServiceConnection.GuardAsync`, поэтому следующий запрос мог использовать
тот же канал и получить поздний ответ на предыдущий запрос.

`IpcClient` закрывает канал при отмене или таймауте уже начатого обмена; интерфейс удаляет
клиента из соответствующего канала запросов и подключается заново. Отмена ожидания очереди
внутри `IpcClient` не закрывает канал текущего запроса.

`IpcCancellationTests` использует настоящие именованные каналы с отдельными именами:
закрытие дескриптора при отмене/таймауте и сохранение первого обмена при отмене второго в очереди.
Проверка доверия системной службе не менялась; внутренний конструктор доступен тестам.

## 4. Таймер AnyConnect продолжал работу после завершения сеанса

Обычный `Timer.Dispose` не дожидался уже выполняющегося callback статистики. После возврата
из `OcSession.Run` владелец освобождал нативный сеанс, а callback мог ещё отправлять команду.

Завершение mainloop теперь дожидается `Timer.DisposeAsync` в `finally`, прежде чем сообщить
о завершении сеанса. Тест `SessionEnd_WaitsForRunningStatisticsCallback` удерживает callback,
завершает mainloop и проверяет, что Run возвращается только после освобождения callback.
В тесте используется подменённая библиотека, реальные переподключения AnyConnect не выполнялись.

## 5. Число динамических IP-закреплений не имело предела

TTL ограничивал возраст записей, но множество новых ответов за час могло неограниченно
увеличивать `_desiredPins`, память и число маршрутов/фильтров. Ограниченный размер DNS-кеша
этот отдельный словарь не ограничивал.

Установлен предел приёма новых IP из DNS — 10 000. При заполнении обновление TTL уже известных
адресов работает, а ответ с новыми адресами отклоняется целиком с SERVFAIL. Истечение TTL
освобождает место. Дубликаты в одном ответе не расходуют дополнительные места.
Служебные закрепления проверки сертификатов через `PinDirect` добавляются отдельно от этого
ограничения; правило ограничивает именно приём новых адресов через `ObservePinnedAsync`.

Тест проверяет заполнение, атомарный отказ, обновление существующей записи и освобождение по TTL.

## 6. Запоздавшие результаты меняли состояние новой попытки

Дозвон и проверка готовности сбрасывали `Dialing`/`Verifying` до проверки номера попытки.
Старый результат мог снять признак текущей операции, преждевременно отпустить очередь дозвонов
или разрешить ещё одну проверку. После разрыва сеанса выполняющаяся проба также не инвалидировалась.
При выключении и повторном включении профиля с тем же ID номера начинались сначала.

Теперь поколение проверяется до изменения состояния; завершение сеанса сбрасывает готовность
и инвалидирует его пробы. Новые номера выделяются на весь срок жизни координатора, поэтому
пересоздание профиля не позволяет принять прежний результат.

Отдельно воспроизведена поздняя проба сертификата после смены сервера: сертификат и узлы
проверки отзыва старого сервера попадали в обновлённый профиль. Проверки сертификата теперь
тоже имеют поколение; смена сервера очищает прежние сведения и инвалидирует старую пробу.

Тесты: три сценария с устаревшим дозвоном/пробой и паузой сначала падали; дополнительно
проверены пересоздание профиля и реально задержанный результат TLS-пробы при смене сервера.

## 7. Отменённая команда оставалась исполняемой в очереди

`SubmitAsync` прекращал ожидание по токену, но отложенная команда всё равно выполнялась,
когда очередь освобождалась. Тест отменял команду включения защиты за занятой очередью:
без исправления намерение всё равно менялось с `Off` на `Protected`.

Перед постановкой и перед началом выполнения теперь проверяется токен вызывающего.
Это не откатывает уже начатую команду. Также это не протокол отмены через IPC: сервер
передаёт токен остановки службы, а отключение клиента само по себе не отменяет команду.

## 8. Таймер накапливал одинаковые работы за занятой очередью

Каждые две секунды создавался новый `Tick`, даже если предыдущий ещё ждал обработки.
В тесте за 50 секунд занятой очереди накопилось 25 тиков. Каждый повторял сверку текущего
состояния и задерживал последующие команды.

В очереди или в работе теперь бывает не более одного тика. Признак сбрасывается в `finally`,
в том числе при ошибке сверки. Остановка основного цикла дожидается завершения задачи таймера.
Ограничение относится к тикам; вся очередь команд не стала ограниченной по размеру.

## 9. Временные служебные DNS-закрепления хранились бессрочно

Кеш закреплённых имён не имел срока жизни. Имена проверки отзыва сертификатов и временные
имена помощника AnyConnect накапливались, как постоянные имена VPN-серверов. У адреса проверки
отзыва маршрут истекал через час, но ответ из закреплённого DNS-кеша обходил обычную обработку
доменного правила и не восстанавливал маршрут.

Временным записям задан час; просроченные удаляются при обращении, добавлении и сверке набора
постоянных имён. После истечения запись снова проходит обычный путь DNS и доменных маршрутов.
Постоянные имена сохраняются для действующих профилей; имена прежних серверов удаляются при
сверке активных профилей. Временная запись не сокращает срок постоянной записи того же сервера.

Добавлены три теста кеша, тест возврата к upstream и обработчику доменных маршрутов после TTL,
а также проверка срока служебного закрепления в сценарии восстановления проверки отзыва.
Это очистка по сроку и актуальности; отдельного общего лимита временных имён не добавлено.

## 10. Смена сервера восстанавливала IP прежнего сервера из файла

Обработчик настроек очищал `ServerAddresses`, но `PreloadServerAddresses` немедленно восстанавливал
старые адреса из `_state.Servers` по ID профиля. Свежая отметка времени откладывала разрешение
нового имени до часа; маршрут и разрешающие фильтры продолжали учитывать прежний сервер.

Теперь смена адреса/протокола или удаление профиля удаляет его сохранённый кеш перед сверкой.
Очищаются и связанные сведения сертификата. Это выполняется также для выключенного профиля,
у которого уже нет записи `TunnelFacts`.

Тест смены имени сначала падал: нового DNS-закрепления не было. После исправления проверены
удаление старого имени, разрешение нового и замена адреса в состоянии туннеля.

## 11. Смена протокола или способа входа сохраняла прежний сеанс

Переподключение сравнивало сервер, имя пользователя и часть полей AnyConnect. Изменение
протокола или способа входа без одновременного ввода нового пароля не разрывало соединение:
настройки уже новые, а работающий сеанс всё ещё поднят по прежним параметрам.

Используется существующий `VpnProtocols.ConnectionKey`, включающий параметры подключения,
аутентификации, EAP и AnyConnect. Несовпадение приводит к завершению прежнего сеанса и
применению новых параметров. Если пароль был удалён из-за смены привязки, служба запрашивает его.
Оба варианта — смена протокола и только способа входа — воспроизведены падающими тестами.

## 12. Служебное закрепление обходило защиту от конфликтов и правила пользователя

`PinDirect` для CRL/OCSP записывал прямую цель без проверки уже закреплённого IP. После ответа
`first.example → VPN` проба сертификата могла получить тот же IP и перенаправить его напрямую.
Служебное разрешение также шло напрямую при явном пользовательском правиле на имя проверки
отзыва, а правило родительского домена перекрывалось более точным служебным правилом.

Теперь служебный ответ проверяется целиком под той же блокировкой: конфликт не меняет ни одного
закрепления и не добавляет ответ в служебный DNS-кеш. Пользовательское правило на имя или его
родительский домен исключает служебное правило и обходное начальное разрешение.

Три тестовых случая подтвердили замену VPN-маршрута и обход точного/родительского правила.
После исправления прежняя VPN-цель сохраняется, а запрещённое начальное DNS-разрешение не вызывается.
Проверены политика, маршруты и вызовы подменённых системных операций; реальный трафик не перехватывался.

## 13. Общий IP двух правил с одной целью терял закрепление раньше срока

Для IP хранились только один суффикс и один срок. Второе правило перезаписывало первое, даже
когда оба требовали тот же VPN. Короткий TTL второго ответа сокращал жизнь первого; удаление
второго правила отзывало закрепление, ещё нужное первому. При прямом маршруте по умолчанию
адрес возвращался на прямой выход раньше срока выданного DNS-ответа.

Желаемый набор хранит владельцев закрепления отдельно по суффиксам. Пока хотя бы у одного
действующего правила не истёк TTL, IP остаётся за общей целью. В политику по-прежнему попадает
одна запись на IP. Число IP ограничено прежними 10 000; владельцы удаляются по TTL и при отзыве
правила. Проверка истечения без изменений не создаёт копию всего словаря каждые две секунды.

Тесты проверяют короткий TTL второго правила, удаление одного владельца и окончательное удаление
IP после истечения TTL оставшегося владельца.

## 14. Отозванное до применения закрепление подтверждалось DNS-клиенту

Пока ответ ждал очередь, пользователь мог удалить правило. Сверка успешно применяла политику
уже без этого закрепления, но ожидающий ответ получал `true` по общему номеру применённого набора.

После ожидания повторно проверяются все адреса ответа: требуемый суффикс, цель и живой TTL должны
остаться в желаемом наборе. Иначе подтверждение не выдаётся и DNS-посредник возвращает отказ.
Тест удаляет правило между постановкой закрепления и обработкой очереди; раньше он получал успех.

## 15. Смена DNS-политики сохраняла временные ответы прежнего пути

`DnsCache.Clear`, вызываемый при смене маршрутов DNS, очищал обычные ответы, но оставлял временные
служебные записи. Такая запись до часа обходила доменный обработчик, даже если новое правило
уже требовало другой путь. Добавленный на предыдущем проходе TTL сам по себе это не устранял.

Смена конфигурации теперь очищает и временные служебные записи. Постоянные имена VPN-серверов
сохраняются, чтобы не нарушить начальное подключение. Это проверено отдельным тестом кеша.

## 16. Поздние результаты возвращали пропущенное обновление и команду установки

Загрузка применяла результат к текущему состоянию без проверки версии/пакета. После команды
«Пропустить» поздний результат переводил пустое состояние в `Ready`. Завершение проверки SHA-256
также могло вернуть команду установки уже пропущенного пакета. Дополнительно команда пропуска
принималась во время установки и удаляла её пакет из учёта и каталога.

Начало и результат загрузки проверяют актуальность пакета и фазу; устаревший результат только
запускает уборку ненужного файла. Подготовка установки проверяет поколение предложения, версию,
путь, контрольную сумму и фазу. Пропуск во время установки получает `Busy`.

Три теста используют подменённый HTTP и временный каталог. MSI в них не запускается.
Уже начатая сетевая загрузка при пропуске может закончиться; её результат не возвращает предложение,
а файл удаляется при обработке завершения. Немедленная отмена сетевого потока здесь не добавлялась.

## 17. Ошибка в продолжении обновления оставляла задачу в вечном ожидании

Продолжения `Update:Check`, `Update:Downloaded` и `Update:Install` присваивали результат
`TaskCompletionSource` только при успехе. Например, ошибка записи `state.json` перехватывалась
циклом службы, но фоновая задача продолжала ждать навсегда. `_work` оставалась незавершённой,
и следующие проверки считались уже идущими.

Добавлена постановка работы с передачей и результата, и исключения ожидающей стороне. Проверка
и загрузка завершаются отказом, ошибки фоновой обработки наблюдаются и записываются в журнал.
Тест блокирует настоящий файл состояния во временном каталоге: запрос должен завершиться
отказом, а после снятия блокировки повторная проверка должна скачать пакет и перейти в `Ready`.
До исправления тест завершался по таймауту.

## 18. Ручная и плановая загрузки списка обходили общее ограничение

Ручные запросы не занимали `_fetch`, поэтому одновременно могли идти несколько загрузок одного
списка. Плановая загрузка освобождала этот признак после постановки результата в очередь,
до применения. Следующий тик мог начать ещё одну проверку. Токен остановки службы не передавался
плановому HTTP-запросу.

Теперь оба пути используют одну операцию на список, занятую до завершения обработки результата.
Повторный ручной запрос получает `Busy`, тик пропускает занятую операцию. Отмена переданного токена
прерывает HTTP и ожидание очереди. Проверены удерживаемый HTTP-запрос, повторный запрос и тик,
ожидание применения готового результата, остановка HTTP и задержка повторной попытки после ошибки.
Это изменение загрузок GeoManager; жизненный цикл остальных фоновых проб службы этим не покрыт.

## 19. Устаревшая загрузка заменяла выбор пользователя

Пока шла загрузка, можно было сменить источник или импортировать список. Пришедший позже ответ
применялся поверх новых данных, причём обработчик выбирал формат разбора уже по текущим настройкам.

Источник и его адреса фиксируются перед HTTP-запросом. В очереди проверяются их актуальность
и поколение ручных операций над списком. Старый ответ после изменения источника, импорта,
отката или решения по ожидающей ревизии отклоняется. Импорт и смена URL проверены тестами
с задержанным ответом. Сам HTTP при смене источника может завершиться; его результат отбрасывается.

## 20. ETag одного адреса отправлялся другому источнику

Состояние хранило только ETag. После смены URL новый сервер мог ответить `304` на чужой валидатор,
и старая база оставалась активной. Аналогичный риск был при переносе ETag зеркала на основной URL.

Добавлен `LastETagUrl`: валидатор используется только для того основного URL, от которого получен,
и при наличии активной базы. Старые файлы состояния без URL вызывают обычную полную загрузку.
Ручной импорт очищает прежнюю привязку, отклонённая загрузка не сохраняет новый ETag.
Тесты проверяют смену URL с одинаковым ETag и сохранение экономного запроса с `304` для прежнего URL.
Ещё один падающий тест подтвердил, что очистка пропусков тоже должна сбрасывать валидатор:
иначе уже скачанная и пропущенная версия остаётся неприменённой из-за `304`, хотя пользователь
снова разрешил её. После очистки пропусков выполняется полная загрузка.

## 21. Подтверждение и откат принимали повреждённую сохранённую ревизию

При активации результат повторной проверки читался, но `IsValid` игнорировался. Откат тоже
мог вернуть непригодную ревизию. Оба сценария воспроизведены повреждением `list.txt` во временном
хранилище после запуска координатора.

Перед изменением политики проверяются описание, идентификатор и содержимое сохранённой версии.
При отказе текущие ревизия и политика сохраняются. Это проверка формата и допустимости списка;
криптографическая проверка сохранённого файла здесь не добавлялась.

## 22. Ошибки записи и отката рассогласовывали файл и действующую политику

Если применение новой базы прошло, а запись `state.json` отказала, память и маршруты оставались
на новой версии при старом состоянии на диске. Обратная ошибка была в откате: сначала сохранялась
старая ревизия, затем применялась политика; ошибка маршрутов не меняла успешный ответ команды.

Активация и откат теперь сначала проверяют ревизию, применяют политику и только затем фиксируют
выбор на диске. При ошибке применения или фиксации возвращаются прежние данные и повторяется
сверка. Исходная ошибка сохраняется в ответе, даже если восстановление очистило `PartialError`.
Если восстановление системы тоже не удалось, это отдельно отражается в ошибке; обычный механизм
повтора сверки сохраняется. Тесты блокируют настоящий файл состояния и отдельно имитируют отказ
маршрутов, проверяя состояние диска, статус и классификацию адреса после отказа и возможность повтора.
Это восстановление после обрабатываемых ошибок, не атомарная транзакция между ОС и диском при аварийном завершении процесса.

## 23. Ошибка уборки старых файлов отменяла результат уже выполненной записи

GeoStore записывал новое состояние, затем удалял старые ревизии. Если старый файл был занят,
исключение уходило вызывающему коду, хотя активная версия на диске уже изменилась.

Ошибки доступа и ввода-вывода при уборке записываются в журнал, но не отменяют успешную фиксацию.
Следующая фиксация повторяет удаление оставшихся каталогов. Тест удерживает файл старой ревизии,
проверяет успешную активацию и удаление остатка после освобождения файла.

## 24. Отправка Cancel могла пересечься с освобождением нативного AnyConnect

После завершения рабочего потока поток команд ещё мог отправлять Cancel. `Dispose` освобождал
нативный сеанс одновременно с этим вызовом. Перехват `ObjectDisposedException` не обеспечивал
синхронизацию владения нативным ресурсом.

`RequestStop` и `Dispose` защищены общей блокировкой; поздняя остановка и повторное освобождение
безопасны. Тест задерживает отправку Cancel после завершения Run и проверяет, что освобождение
ждёт окончания команды. Как и в пункте 4, библиотека в тесте подменена; реальные сеансы VPN не запускались.

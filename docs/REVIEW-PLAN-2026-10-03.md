## Находки

### 1. P1 — ограничения чтения пользовательских файлов не ограничивают расход ресурсов

Источник: [DiagnosticsCollector.cs](D:/VPN/src/SplitVpn.Service/Diagnostics/DiagnosticsCollector.cs:168), `AddUserFile` / `ReadConfined`; также расчёт бюджета профиля на строках 103–114.

Начальная длина проверяется до чтения, затем `input.CopyTo(buffer)` читает до конца без лимита. Размер проверяется повторно только после завершения копирования. Файл открыт с разрешением другим процессам писать в него. Поэтому файл, выросший после начальной проверки, сначала целиком попадает в `MemoryStream`, и только затем отвергается. Бюджет профиля вычитается по длине, измеренной ещё до открытия, а не по фактически прочитанному объёму.

После 10 секунд `read.Wait` возвращает управление, но сама задача чтения не отменяется и не завершается принудительно. Следующий сбор может запускать новые чтения, пока прежние удерживают потоки и дескрипторы. Ограничение одного одновременно собираемого архива это не ограничивает: сбор может закончиться с пропущенными файлами, а чтения продолжатся.

Последствие: расход памяти и накопление незавершённых чтений в процессе службы с правами SYSTEM под влиянием файлов обычных пользователей. Исчерпание памяти или потоков на рабочей службе не воспроизводилось; основание — статический разбор конкретного пути чтения. Это не подтверждение обхода `ConfinedFile` или чтения чужих защищённых файлов.

Исправить: копировать не более минимального из остатка бюджета профиля и лимита файла, читать максимум один дополнительный байт для обнаружения превышения. Учитывать реально принятые байты. Ограничить число незавершённых чтений на весь срок работы службы, включая операции после таймаута; слот освобождать только при фактическом завершении. Простое добавление `CancellationToken` не доказывает отменяемость зависшего синхронного открытия файла.

### 2. P2 — нет предела количества и общего объёма готовых архивов

Источник: [DiagnosticsPackages.cs](D:/VPN/src/SplitVpn.Service/Diagnostics/DiagnosticsPackages.cs:42), `Create`.

`_building` ограничивает только одновременную сборку. Последовательные запросы создают новые файлы, даже если предыдущие архивы не забраны. До истечения 15 минут они остаются на диске; очистка запускается раз в минуту. При нескольких клиентах или повторных попытках после потери ответа каталог растёт без общего лимита.

Воспроизведение: 24 последовательных вызова `Create` без чтения результата приняли все 24 архива и оставили 25 165 824 байта. Тестовые архивы по 1 МиБ; реальный сбор может включать существенно больше данных. IPC требует администратора интерактивного сеанса, поэтому это не прямой доступ любого пользователя к команде создания.

Исправить: ввести предел числа сохранённых пакетов и суммарного размера каталога; ограничить размер пакета в процессе записи, до заполнения диска. При исчерпании квоты возвращать понятный отказ, удалять незавершённый файл. Не удалять пакет, который ещё читает другой клиент, ради новой сборки. TTL оставить как дополнительную очистку.

### 3. P2 — дата одного файла срывает весь сбор

Источники: [DiagnosticsCollector.cs](D:/VPN/src/SplitVpn.Service/Diagnostics/DiagnosticsCollector.cs:190), `AddUserFile`; [DiagnosticsArchive.cs](D:/VPN/src/SplitVpn.Core/Diagnostics/DiagnosticsArchive.cs:175), `AddClientFile`.

При присваивании `LastWriteTime` ZIP принимает только даты в диапазоне 1980–2107. Значение напрямую берётся из файла. `ArgumentOutOfRangeException` не попадает в фильтры обработки ошибки отдельного файла. Для пользовательского файла оно выходит из сборщика, а `CollectDiagnostics` также перехватывает только ошибки IO и доступа: клиент теряет часть службы вместо архива со списком проблем. Клиентская часть может затем оборвать и создание итогового ZIP.

Воспроизведение: обычный синтетический `ui-verbose.log` с `LastWriteTimeUtc = 1979-01-01` вызывает `ArgumentOutOfRangeException` отдельно у обоих сборщиков. Удаление файла после чтения тоже создаёт риск: повторное чтение метаданных по пути уже не относится к открытому файлу.

Исправить: единый небольшой механизм нормализации времени ZIP, использовать допустимое значение по умолчанию и записывать причину в `Problems`, когда исходная дата некорректна. Для пользовательского файла возвращать данные и метаданные из операции безопасного чтения, не запрашивать путь повторно после неё. Распространить нормализацию на остальные добавления файлов. Архив должен сохраняться при сбое одного источника.

Документация ограничения даты: [Microsoft, ZipArchiveEntry.LastWriteTime](https://learn.microsoft.com/en-us/dotnet/api/system.io.compression.ziparchiveentry.lastwritetime).

### 4. P2 — при большом журнале Windows пропадают последние события

Источник: [SystemDiagnostics.cs](D:/VPN/src/SplitVpn.Service/Diagnostics/SystemDiagnostics.cs:142), `Export`.

У `EventLogQuery` не задано `ReverseDirection`; локальный стенд подтвердил значение `false`. Чтение идёт от старых событий к новым, а цикл прекращается после 2000 подходящих записей. Если их больше за выбранные трое суток, архив содержит начало окна, а последние события, ради которых обычно собирают диагностику, отбрасываются. Явного уведомления об усечении нет.

Дополнительно цикл получает следующую запись в выражении обновления прежде, чем снова проверяет `count < MaxEvents`. Первая запись за пределом лимита не попадает в `using (record)` и не освобождается явно.

Исправить: читать с `ReverseDirection = true`, брать последние события; при необходимости выводить выбранные записи в хронологическом порядке. Отдельно сообщать об усечении. Переписать цикл так, чтобы каждая полученная запись, включая проверку наличия дополнительных событий, гарантированно освобождалась. Для журналов с фильтрацией по тексту учитывать отдельно просмотренные и включённые записи.

Основание порядка чтения: локально проверенное значение и [исходники Microsoft EventLogQuery](https://github.com/microsoft/referencesource/blob/main/System.Core/System/Diagnostics/Eventing/Reader/EventLogQuery.cs). Полный экспорт журнала рабочей машины в этом ревью не выполнялся.

## План исправлений

Чистые алгоритмы чтения/отбора проверять через управляемые потоки и подменённый источник событий; отдельную проверку блокирующего Windows-открытия проводить на изолированных файлах.
2. Закрыть P1: ограниченное чтение с фактическим бюджетом, единый ограничитель операций, наблюдение за завершением оставшихся после таймаута задач. Проверить, что повторные сборы не увеличивают число зависших операций сверх лимита и не удерживают очередь координатора. При остановке не ждать бесконечно блокирующее открытие; если управляемое ограничение не даёт достаточной изоляции, отдельно обосновать помощник, а не вводить его заранее.
3. Ограничить хранение пакетов: квоты количества и размера, отказ до бесконтрольного роста, ограничение записи и гарантированное удаление неполного результата. Проверить параллельное чтение, сбор, очистку и удаление последнего куска.
4. Исправить обработку времени/ошибок отдельных файлов. При повреждённом или исчезнувшем источнике сохранить остальные части, корректный ZIP и объяснение в манифесте. Проверить итоговое сообщение UI/CLI о частичном результате.
5. Исправить выбор событий и освобождение записей. Проверить порядок, лимит, текстовую фильтрацию и сообщение об усечении.
6. Выполнить полные Release-тесты и сборку решения; проверить сбор архива при недоступной службе, недоступном пользовательском файле и прерывании передачи. Нативные сценарии службы и зависшего открытия проверять отдельно на стенде, где разрешены установка и перезапуск.

Критерий готовности: конечные бюджеты памяти/потоков/диска реально соблюдаются; одиночный проблемный файл не уничтожает архив; свежие события сохраняются; существующие проверки не регрессируют. После ревью пользователь разрешил реализацию и выпуск релиза. Установка и изменение рабочей службы не запрошены.

## Реализация

Все четыре группы исправлены для выпуска 0.10.0. Пользовательский файл читается максимум до лимита плюс один контрольный байт, бюджет профиля расходуется по фактическому результату. Общий ограничитель допускает не больше двух незавершённых операций между сборами; после таймаута слот остаётся занятым, ошибка завершившейся фоновой задачи наблюдается. Синхронное открытие принудительно не прерывается, но новые операции не накапливаются.

Готовые пакеты ограничены тремя файлами, 256 МБ на пакет и 512 МБ суммарно. Поток проверяет квоту до записи, в том числе при закрытии ZIP; даже перехваченная сборщиком ошибка квоты не позволяет зарегистрировать неполный пакет. Прежние пакеты сохраняются до выдачи/TTL.

Дата нормализуется общим ArchiveTime, метаданные пользовательских файлов и файлов клиентского архива читаются по открытому дескриптору. UI сообщает о замечаниях; CLI уже выводил их. ExportRecords выбирает последние 2000 подходящих событий, явно сообщает об усечении и освобождает все полученные записи, включая контрольную лишнюю.

Добавлены 10 регрессионных случаев: даты 1979/2108 в обоих архивах; квоты количества, отдельного и общего размера; перехваченная ошибка квоты; бесконечно растущий поток; повторные обращения после таймаута; свежие события, фильтрация и освобождение записи за лимитом. Первый полный прогон: 987 всего, 983 успешно, 4 прежних пропуска SecretStore, 0 ошибок. После удаления предварительного чтения длины по пути (защита от исчезновения файла) проверки повторяются штатным выпуском.

В скрипте выпуска исправлено чтение Content-Length как массива строк в PowerShell 7. Релиз выпускается существующим механизмом публичного снимка без приватной истории, с подписанным манифестом.

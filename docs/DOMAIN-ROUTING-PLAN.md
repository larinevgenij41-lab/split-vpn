# План доменной маршрутизации

## Цель и границы

Добавить правила вида «доменный суффикс → цель» для IPv4: напрямую, через выбранный VPN-туннель или блокировать. Правило `example.com` действует на само имя и на поддомены, но не на `notexample.com`.

Реализация использует существующий локальный DNS-посредник и динамические host-маршруты `/32`. Она не является маршрутизацией по имени на уровне пакета: после DNS-разрешения Windows видит только IP-адрес назначения. Поэтому DoH, жёстко заданный DNS, прямое обращение по IP и общий IP у доменов с разными целями требуют явно описанного поведения.

План рассчитан на модель v2 `RouteTarget`, но первый рабочий срез можно проверить с одним основным туннелем: домен «Напрямую» поверх общего маршрута через VPN и домен «Через основной VPN» поверх общего прямого маршрута.

## Пользовательская семантика

- В настройках хранится `DomainRuleSetting { Id, Suffix, Target, Comment? }`.
- Суффикс нормализуется: пробелы и конечная точка удаляются, регистр игнорируется, Unicode переводится в IDNA ASCII. Пустые метки, IP-литералы и произвольные маски `*` запрещены.
- Совпадение выполняется по границе DNS-метки. При нескольких совпадениях выигрывает самый длинный суффикс.
- Одинаковые нормализованные суффиксы запрещены. Пользовательское правило не может перекрывать локальный DNS-суффикс: локальные имена всегда обслуживает DNS основной сети.
- Доменное назначение имеет приоритет над Default, RU-базой и CIDR-правилами, потому что создаёт более точный `/32`. Служебные адреса VPN-серверов, DNS службы, loopback, on-link и локальные диапазоны переопределять нельзя.
- Если выбранный туннель не поднят или маршрут нельзя установить, запрос завершается `SERVFAIL`; отката на другой туннель или прямой путь нет.
- «Блокировать» отвечает `REFUSED` без обращения к upstream. Это не маскируется под несуществующий домен и не создаёт долгий отрицательный кеш `NXDOMAIN`.
- Пока IPv6-маршрутизация не реализована, для совпавшего неблокирующего правила запрос `AAAA` получает пустой успешный ответ, чтобы приложение использовало управляемый IPv4. Публичный IPv6 при включённой защите остаётся заблокирован глобально.

## Поток одного DNS-запроса

| Шаг | Действие | Условие безопасности |
|---|---|---|
| 1 | Нормализовать QNAME и выбрать самое специфичное правило | локальные суффиксы проверяются раньше пользовательских |
| 2 | Выбрать upstream DNS и интерфейс цели | Direct — исходный DNS через основной адаптер; Tunnel — DNS выбранного туннеля через его interface index |
| 3 | Переслать запрос и разобрать CNAME/A с TTL каждой записи | ответ ещё не отдан приложению |
| 4 | Передать адресные leases в очередь координатора и дождаться применения `/32` и WFP | при ошибке или таймауте вернуть `SERVFAIL`, не отдавать адрес |
| 5 | Записать ответ в кеш с поколением политики и вернуть клиенту | соединение начинается только после готовности маршрута |
| 6 | По ближайшему сроку удалить истёкшие leases и выполнить облегчённую сверку | маршрут остаётся, пока есть хотя бы один действующий lease той же цели |

Ключевой инвариант: **сначала маршрут и защита, потом DNS-ответ**. Асинхронное `Pin` после ответа создаёт утечку в окно между DNS и первым TCP/UDP-соединением и поэтому не подходит.

## CNAME, TTL и общий IP

- `DnsMessage` расширяется безопасным обходом Answer и Additional: извлекаются A-записи, CNAME-цепочка, TTL каждой записи и флаг усечения. Сжатые DNS-имена проверяются на циклы и выход за границы сообщения.
- Если ответ содержит только CNAME, правило временно наследуется каноническим именем. Последующий запрос A для canonical name использует исходную цель, даже если само canonical name не входит в суффикс.
- Срок address lease равен минимальному TTL связанной CNAME/A-цепочки, ограниченному диапазоном 60 секунд — 1 час. Ответ в кеше никогда не живёт дольше маршрута.
- Реестр хранит claims `(address, ruleId, target, expiresAt)`. Несколько доменов с одной целью могут совместно удерживать один `/32`.
- Если IP уже имеет активный claim другой цели, существующий маршрут не меняется, новый DNS-ответ клиенту не отдаётся (`SERVFAIL`), а в статусе появляется обезличенное предупреждение о конфликте shared IP. Стратегия «последний запрос победил» запрещена: она молча отправила бы уже работающий домен не туда.
- После истечения конфликтующих claims следующий DNS-запрос может успешно назначить адрес новой цели.

## Изменения по слоям

### Core

- `Settings/AppSettings.cs`: добавить `DomainRules`; включить их в миграцию схемы v2.
- `Settings/SettingsValidator.cs`: нормализация/IDNA, дубликаты, пересечение с локальными суффиксами, существование и активность `TunnelId`, лимиты правил.
- Новый `Dns/DomainRuleMatcher.cs`: неизменяемый longest-suffix matcher без регулярных выражений.
- Расширить `Dns/DnsMessage.cs`: `BuildRefused`, `BuildNoData`, разбор CNAME/A/TTL.
- Новый `Dns/DomainLeaseTable.cs`: claims, CNAME-наследование, конфликты, истечение и лимиты. Хранить только в памяти.

### Windows и DNS-посредник

- `DnsProxyConfiguration` получает неизменяемый снимок правил, `PolicyGeneration` и маршруты Direct/по туннелям.
- `DnsProxyServer.HandleAsync` использует `IDomainRouteSink.ApplyBeforeReplyAsync(...)`; callback вызывается только для валидного неусечённого ответа с адресами.
- Ключ кеша включает поколение политики и фактический route target. При смене настроек кеш посредника очищается.
- Direct lease создаёт `/32` через gateway/LUID основного адаптера; Tunnel lease — `/32` с next hop 0 на LUID туннеля; для Direct добавляется узкая динамическая WFP-permit запись. Все динамические объекты остаются узнаваемыми штатной меткой проекта.

### Служба

- Координатор владеет `DomainLeaseTable`; DNS-потоки отправляют команды в его однопоточную очередь и ждут завершения облегчённого `EnsureDomainRoutesAndProtection`.
- Запросы для одного адреса/цели объединяются. Очередь ограничена; таймаут применения — 2 секунды. Переполнение или таймаут дают `SERVFAIL` и счётчик ошибки, но не обход политики.
- Таймер ставится на ближайшее истечение, а 60-секундная полная сверка остаётся страховкой от дрейфа.
- При сохранении правил, смене роли профиля, переподключении или смене основного адаптера: увеличить поколение, очистить DNS-кеш и leases, сверить маршруты/WFP, затем сбросить системный DNS-кеш. При старте службы сначала удалить оставшиеся динамические маршруты общей сверкой и сбросить системный DNS-кеш.
- Для упавшего туннеля не выдавать новые ответы его доменов. Уже выданные адреса блокировать динамической WFP-группой до истечения lease или восстановления туннеля, чтобы они не ушли через основной маршрут.
- В статус вывести только количества: активные доменные правила, leases, конфликты, ошибки применения и ближайшее истечение. Имена доменов и адреса не писать в обычный журнал.

### Интерфейс и диагностика

- На доске маршрутизации домен — отдельная карточка. Добавление доступно из каждой колонки; редактируются суффикс и комментарий, цель задаётся колонкой.
- Перед сохранением показывать нормализованное значение и ошибки. Для правила добавить действие «Проверить»: выполнить запрос через службу и показать выбранную цель, upstream, адреса, TTL и факт установки маршрута.
- Общие предупреждения в UI: «Работает только через системный DNS», «DoH и прямой IP обходят правило», «Общие CDN-IP нельзя одновременно направить в разные цели».
- Диагностическая команда показывает обезличенную сводку по leases; подробные домены доступны только по явной одноразовой проверке и не сохраняются в отчёт автоматически.

## Ограничения и лимиты

- IPv4-only до отдельного этапа IPv6.
- Не более 1 000 правил, 1 024 активных адресов на правило и 10 000 claims всего. Превышение — `SERVFAIL` для новых адресов с видимой ошибкой в UI.
- DNSSEC не валидируется посредником самостоятельно; ответ пересылается как получен. Модификация ответа ограничена синтетическими `REFUSED`/NODATA и TTL кеша.
- QUIC не требует отдельной логики: после корректного `/32` UDP следует той же таблице маршрутов. ECH не мешает, поскольку правило применяется на DNS-этапе до TLS.
- Доменные правила не гарантируют разделение разных имён на одном IP; описанное fail-closed поведение предотвращает неверную маршрутизацию ценой недоступности второго имени.

## Этапы и контрольные точки

| КТ | Содержание | Критерий приёмки |
|---|---|---|
| D0 — спайк | На одном туннеле: запрос → временный `/32` → TCP/QUIC-проба; измерить применение до ответа; CNAME на реальном CDN | 100 повторов без пакета на неверном интерфейсе; маршрут виден до возврата DNS-ответа |
| D1 — Core | matcher, нормализация, парсер RR, lease table, конфликт shared IP, миграция/валидация | property/fuzz-тесты DNS-парсера; unit-тесты TTL, CNAME, longest suffix, IDNA и конфликтов |
| D2 — DNS/служба | callback до ответа, очередь актора, динамические маршруты/WFP, сброс кешей, истечение | интеграционные тесты на фейках и dev-службе; ошибка применения всегда `SERVFAIL` без fallback |
| D3 — UI | карточки доменов, редактирование, проверка, статусы/предупреждения | UIA: мышь, клавиатура, обе темы; сохранение и перенос карточки меняют фактический маршрут |
| D4 — отказоустойчивость | рестарт службы, смена сети/цели, падение туннеля, лимиты, recover/uninstall | старые `/32` и кеш не переживают смену политики; падение туннеля не даёт утечки; recover снимает все объекты |
| D5 — поставка | документация, сценарий `kt7-domain`, MSI | обновление в Connected сохраняет настройки; полный сценарий проходит с возвратом системы в безопасное состояние |

## Обязательная матрица тестов

1. Apex и поддомен совпадают, похожий суффикс не совпадает; длинный суффикс выигрывает.
2. Unicode/IDNA, регистр и конечная точка дают один ключ; дубликат отклоняется.
3. Direct поверх общего VPN и Tunnel поверх общего Direct подтверждаются `GetBestRoute2`, локальным адресом сокета и `pktmon`.
4. CNAME с A в том же ответе и CNAME с отдельным последующим запросом устанавливают одну цель.
5. TTL 0/30/60/3600/86400, продление lease и совместное владение адресом одной целью.
6. Один IP у двух целей: первая остаётся неизменной, вторая получает `SERVFAIL`, утечки нет.
7. Смена цели при заполненном кеше: старый кеш и `/32` удалены, системный кеш сброшен, следующий запрос идёт по новой цели.
8. Туннель падает между upstream-ответом и применением: DNS-ответ не возвращается, адрес блокируется.
9. Рестарт/kill службы и внешнее удаление `/32` или WFP-фильтра: безопасное восстановление без сохранения доменных имён на диск.
10. DoH включён: UI и документация честно показывают обход; обычный системный DNS продолжает работать по правилу.

## Зависимости и порядок включения в v2

Доменный слой зависит от `RouteTarget` и стабильных идентификаторов туннелей, но не должен ждать готовности всей доски или второго VPN-сервера. Выполнить D0–D2 после модели КТ7.1; проверить цели Direct/Primary на одном сервере. Цель Secondary добавить в матрицу после прохождения multi-tunnel спайка КТ7.0. В UI КТ7.3 использовать уже готовые API доменных правил, а не встраивать DNS-логику во ViewModel.

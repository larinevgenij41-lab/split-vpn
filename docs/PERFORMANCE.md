# Оптимизация DNS и сборки политики — 2026-09-24

В `IntervalPainter.Paint(RangeSet)` слой из одного диапазона теперь использует существующую
точечную покраску. Добавление loopback, сети адаптера или адреса сервера больше не создаёт
копию всей разметки IPv4. Для больших слоёв сохранён однопроходный алгоритм.

В `DnsProxyServer.HandleAsync` найденное доменное правило используется повторно при выборе
DNS-пути. Поиск наиболее длинного суффикса выполняется циклом; сопоставление суффиксов
использует span и сравнение без учёта регистра без создания строк. Сохранены границы
DNS-меток, приоритет более длинного суффикса и первого правила при равной длине.

## Замеры

Windows x64, .NET SDK 10.0.401, Release. Исходный код — `24039c7`, новая версия — рабочие
изменения поверх него. Один и тот же `tools/Performance` запущен последовательно на обеих
версиях. Tiered compilation отключена в проекте замеров, чтобы переходы JIT между уровнями
не искажали сравнение коротких операций. 200 прогревочных операций, затем медиана пяти серий:
по 100 сборок политики или по 20 000 DNS-запросов.

| Операция | Было | Стало | Выделено памяти: было → стало |
| --- | ---: | ---: | ---: |
| Сборка политики: 10 тыс. диапазонов RU + 20 тыс. обхода | 16,564 мс | 11,698 мс | 33 446 054 → 21 430 505 байт |
| DNS из кеша, 0 доменных правил | 0,777 мкс | 0,555 мкс | 1 472 → 816 байт |
| DNS из кеша, 20 доменных правил | 1,996 мкс | 0,892 мкс | 3 792 → 848 байт |
| DNS из кеша, 200 доменных правил | 12,585 мкс | 4,371 мкс | 25 536 → 848 байт |

Сборка политики: время −29%, выделение памяти −36%. DNS с 200 правилами: примерно в 2,9 раза
быстрее, выделение памяти −97%. Выделенные байты — сумма аллокаций на операцию, не размер
рабочего набора процесса. Входы синтетические и воспроизводимые; это не замер пропускной
способности VPN, задержки upstream DNS или реальной минутной сверки Windows.

## Нужна ли СУБД

Для устранения найденных расходов СУБД не требуется: обе операции работают в памяти.
`GeoManager.ActiveSet` уже хранит активные диапазоны в `RangeSet`, а `StoreState` кеширует
метаданные списка. DNS-кеш — словарь в памяти; `EventJournal` ограничен 500 событиями.
Настройки и состояние сохраняются атомарными файлами через `ServiceStores`.

SQLite стоит рассмотреть при добавлении постоянной истории подключений, статистики,
поиска и фильтрации событий или транзакционных изменений множества связанных записей.
Она подходит как встроенное локальное хранилище: [SQLite как формат файла приложения](https://www.sqlite.org/appfileformat.html).
При таком переходе служба должна владеть БД, а интерфейс продолжать обращаться к службе
через IPC; рабочие диапазоны и DNS-кеш разумно оставить в памяти. Запрошенные DNS-имена
сейчас намеренно не пишутся на диск — миграция хранилища не должна менять это поведение.

Пока измеренных оснований для миграции нет. Перед её реализацией нужны сценарий хранения
и замер чтения/записи. Также нужно учитывать, что async-методы `Microsoft.Data.Sqlite`
выполняются синхронно: [ограничения провайдера](https://learn.microsoft.com/en-us/dotnet/standard/data/sqlite/async).

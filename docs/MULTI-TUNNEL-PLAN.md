## Что дало слияние с протоколами

- **Версия схемы настроек — 3.** Обе стороны независимо подняли её до 2, поэтому миграция разбирает оба вида: профили схемы 1 приводятся к SSTP с MS-CHAP v2, а «активное подключение» и «режим маршрутизации» становятся ролью опорного туннеля и целями. Прежний файл сохраняется как `settings.json.v1.bak`.
- **Запись телефонной книги — одна на профиль.** Подготовка записи принимает имя, профиль и ключ IPsec; конфигурация EAP готовится для каждой записи отдельно, при удалении профиля запись и ключ уходят вместе с ней.
- **Транспорт WFP — по протоколу каждого туннеля.** SSTP пропускается по TCP на своём порту, L2TP/IPsec — UDP 500/4500/1701 и ESP, IKEv2 — UDP 500/4500 и ESP, PPTP — TCP 1723 и GRE. Туннели с разными протоколами работают одновременно.
- **Отпечаток параметров входа хранится по профилю.** Соединение, поднятое с другим протоколом или способом входа, не подхватывается после перезапуска службы, а разрывается.

## Находки при реализации

- **Выключенный на ходу туннель не разрывался.** Профиль, у которого сняли роль, просто исчезал из фактов координатора, а соединение RAS оставалось поднятым. Разрыв добавлен в шаг синхронизации туннелей; на это есть тест.
- **Неизвестное имя значка WPF-UI вешает раскладку.** `Icon="{ui:SymbolIcon Broadcast24}"` — такого значения в `SymbolRegular` нет; вместо ошибки страница не отрисовывается и процесс перестаёт отвечать. Имя значка проверять по метаданным сборки.
- **Вложенная горизонтальная прокрутка на доске не нужна.** Колонки переносятся `WrapPanel`: вторая `ScrollViewer` внутри страницы снова забирала бы колёсико мыши.
- **Откат на прежнюю версию после миграции.** Схему 2 старая служба не прочитает и запустится с пустыми настройками — это ровно тот сценарий, который в v1 привёл к зависшей защите без выхода. Поэтому при первой миграции прежний файл сохраняется рядом как `settings-v1.json`, а в журнал пишется строка об этом.
- **Гонка в фейках, а не в продукте.** Два параллельных дозвона меняли общий `HashSet` поднятых туннелей, из-за чего тест группы падал примерно в одном запуске из четырёх. Фейки сделаны потокобезопасными.

# План v2: несколько одновременных туннелей и визуальная маршрутизация

## Контекст

Запрос 2026-09-13: использовать сразу несколько VPN-подключений с удобной визуальной настройкой маршрутизации; по возможности — маршрутизация для конкретных приложений.

Решения пользователя (2026-09-13):
- **Правила по приложениям — не делаем.** Перенаправить трафик процесса в другой туннель Windows умеет только через подписанный callout-драйвер WFP (недоступно для личного проекта); заменители (прокси на туннель, ограничение приложения через `ALE_APP_ID`) отклонены. Записать в `LIMITATIONS.md` с причиной.
- **Правила по доменам — включить**: «суффикс → цель», DNS-посредник разрешает имя через нужный путь и ставит маршруты на полученные адреса на время TTL. Детальная семантика, fail-closed обработка и контрольные точки — в `DOMAIN-ROUTING-PLAN.md`.
- **Интерфейс — доска с колонками и перетаскиванием**: колонки «Напрямую», по одной на туннель, «Блокировать»; карточки — «Россия (RU-база)», «Остальной интернет», сети, домены.
- **Второй SSTP-сервер даст пользователь** (адрес и логин в чат, пароль — окно консоли или одноразовый файл).
- **Реализация в отдельной ветке.** В `D:\VPN` сейчас ветка `codex/vpn-protocols` с чужими незакоммиченными правками (протоколы L2TP/IPsec, IKEv2, PPTP: `ConnectionProfile.Protocol`, `VpnProtocols`, транспортные фильтры по протоколу). Её не трогаем: работаем в **отдельном worktree** `D:\VPN-multi` на ветке `feature/multi-tunnel` от `main` (`1f6195c`). Точки будущего слияния: `AppSettings.ConnectionProfile`, `SettingsValidator.ValidateProfile`, `FilterPlan.AddServerTransport` (транспорт «по туннелю» × «по протоколу» — оба нужны).

Фактура (проверено): на всех интерфейсах строгая модель хоста (`Weak Host Sends: disabled`) — сокет с привязкой к адресу туннеля уходит только через него при наличии маршрута на нём; миниportов SSTP 65 535; RAS допускает несколько записей и одновременных соединений в своём pbk; DNS-посредник уже выбирает путь по суффиксам (`LocalSuffixes`) и умеет закреплять адреса (`Pin`); разрешение туннеля в WFP — по LUID на весе 12, прямые диапазоны — `FWP_RANGE` на весе 6.

## Модель

- **Туннель = профиль подключения.** Роль: `Primary` (основной: маршруты по умолчанию `0.0.0.0/1` и `128.0.0.0/1`, DNS по умолчанию), `Secondary` (дополнительный: получает только явно назначенные сети и домены — точные маршруты на его интерфейс, маршрутов по умолчанию нет), `Off`. Активны одновременно основной и все дополнительные. Основной может отсутствовать («Остальной интернет → Напрямую»: VPN только для выбранных сетей).
- **Цель маршрутизации** `RouteTarget { Kind: Direct | Tunnel | Block; TunnelId? }`. Назначаются: «Россия (RU-база)» (по умолчанию Direct), «Остальной интернет» (по умолчанию основной туннель), каждая сеть CIDR, каждый домен. Это заменяет `RoutingMode`: `RussiaDirect` ≡ Geo→Direct, `AllViaVpn` ≡ Geo→основной.
- **Порядок политики** (как в v1): остальной интернет → гео → сети по длине префикса → доменные host-маршруты → зарезервированные/локальные → серверы всех туннелей (транспорт через основной адаптер). Домены — динамические `/32` на время TTL ответа (не меньше 60 с, не больше 1 ч); локальные и служебные адреса они не переопределяют.
- **Обрыв.** Основной туннель упал — как в v1 (блокировать назначенное VPN / всё / разрешить всё). Дополнительный упал — его сети блокируются (не должны утечь в основной), домены его не резолвятся до восстановления; повторный дозвон с той же выдержкой.
- **Метки маршрутов.** Метрика 3917 остаётся для всех своих маршрутов (маршруты по умолчанию — только на основном, поэтому вторая метрика не нужна). Проверка дополнительного туннеля — TCP-проба к цели с привязкой к адресу туннеля и временным маршрутом `/32` цели на его интерфейс.

## Риски

- Сервер может не давать двух сессий одного пользователя — поэтому второй сервер.
- Рост числа фильтров: только `Dynamic` меняется часто (десятки host-разрешений); группа `Direct` (19 тыс.) пересобирается лишь при смене цели гео.
- Доменные правила зависят от системного резолвера: браузеры с DoH их обойдут. Общий CDN-IP нельзя одновременно направить в разные цели; конфликт обрабатывается fail-closed (`SERVFAIL` для нового назначения), а не молчаливой сменой маршрута. Ограничения и тесты описаны в `DOMAIN-ROUTING-PLAN.md`.
- Слияние с `codex/vpn-protocols`: конфликт в трёх файлах, разрешение вручную; транспортные фильтры должны учитывать и туннель, и протокол.

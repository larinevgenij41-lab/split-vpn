## Цель и границы

В существующем приложении выбирать протокол подключения и способ входа, сохраняя
разделение трафика, DNS-посредник, защиту при обрыве, переподключение и восстановление сети.

Согласованный набор протоколов: **SSTP, L2TP/IPsec, IKEv2, PPTP**.
WireGuard и OpenVPN исключены пользователем из этой ветки.
Используем Windows RAS и EAPHost, не пишем собственные реализации протоколов и криптографии.

> **Исключение (2026-09-14):** Cisco AnyConnect подключается через libopenconnect (LGPL-2.1) в отдельном
> процессе-помощнике, а не через RAS: в Windows нет встроенной реализации протокола. Это осознанное расширение
> правила «только RAS», согласованное пользователем; собственной реализации протокола и криптографии по-прежнему нет.
> Решения и ограничения — [ANYCONNECT-PLAN.md](ANYCONNECT-PLAN.md).

EAP-MSCHAPv2 — способ аутентификации, а не алгоритм шифрования. В интерфейсе отдельно
показываем «Протокол», «Способ входа» и, для L2TP/IPsec, «Проверка IPsec».
TLS/IPsec/MPPE обеспечивают защиту транспорта. В этой итерации используются системные
криптографические политики Windows; отдельный редактор AES/DH/PFS и глобальные изменения
Schannel/IPsec в объём не включены. Это предлагаемая граница плана, а не уже согласованное решение.

## Предлагаемые способы входа

| Способ | Данные и параметры | Назначение |
|---|---|---|
| MS-CHAPv2 | Логин, пароль, необязательный домен | Сохранить существующий вход; SSTP/L2TP/PPTP |
| EAP-MSCHAPv2 | Логин, пароль, необязательный домен; EAP type 26 | Прежде всего IKEv2, также совместимые профили RAS |
| PEAP с EAP-MSCHAPv2 | Логин/пароль, ожидаемые имена сервера аутентификации, доверенные CA | Вход по паролю с проверкой TLS-сервера внутри PEAP |
| EAP-TLS | Клиентский сертификат с закрытым ключом, ожидаемые имена сервера и CA | Вход по сертификату без требования пароля пользователя |
| EAP-TTLS с MSCHAPv2 или PAP | Логин/пароль, имена сервера и CA, внутренний метод | Совместимость с серверами TTLS; проверить работоспособность в службе |
| PAP / CHAP | Логин/пароль | Явно выбранный режим совместимости для SSTP/L2TP; не включать по умолчанию |

Это целевой набор на согласование. Не выдавать существование EAP-метода в Windows за
проверенную совместимость с каждым транспортом и запуском от LocalSystem.
Первый этап уточняет матрицу доступных сочетаний на изолированных RAS-записях и стенде.
Если конкретное сочетание невозможно, зафиксировать причину и согласовать изменение объёма,
а не незаметно исключать его из результата.

Правила сочетаний:

- IKEv2: EAP либо отдельный режим машинного сертификата; обычные PPP PAP/CHAP/MS-CHAPv2 не предлагать.
- L2TP/IPsec: PSK или машинный сертификат для IPsec, независимо от способа входа пользователя.
- PPTP: обязательное MPPE; только методы, дающие необходимые ключи. PAP/CHAP для PPTP не предлагать.
- EAP-TLS: пароль не обязателен. Выбор сертификата должен работать при дозвоне службой без диалогов.
- PEAP/TTLS: проверка сертификата сервера обязательна, внутренний PAP не равен передаче PAP без TLS.
- PPTP помечать как устаревший, выбирать его только явно. Не делать автоматический переход между протоколами.

## Подтверждённая исходная архитектура

- `ConnectionProfile` не содержит протокол; `AuthMethod` содержит только `MsChapV2`.
- `RasPhonebook.Build` всегда выбирает SSTP и MS-CHAPv2; `IRasOps.SaveEntry` принимает только сервер.
- `Coordinator.StartDial` кеширует запись по строке сервера. Смена протокола/аутентификации
  при том же сервере сейчас не учитывается.
- `RasClient.GetProjection` читает PPP-часть объединения; IKEv2 требует отдельной ветки.
- WFP разрешает транспорт сервера только по TCP на SSTP-порт.
- Пароли передаются отдельным IPC-запросом, хранятся через DPAPI и ACL; JSON профиля не содержит секретов.
- Редактор и мастер первого запуска рассчитаны на обязательный логин/пароль SSTP.
- Служба работает от LocalSystem. Сертификат из CurrentUser интерактивного пользователя
  не становится автоматически доступен службе.

## Этапы и критерии перехода

### 1. Проверить возможности RAS/EAP до разработки рабочих модулей

- Подтвердить флаги RAS для четырёх протоколов и выбранных методов по SDK и документации Microsoft.
- На отдельной телефонной книге проверить создание, чтение и удаление записей, запись PSK,
  генерацию EAP-конфигурации через Windows API, получение проекции IKEv2.
- Проверить передачу EAP-учётных данных в асинхронный RasDial без UI и автоподстановки
  учётных данных Windows; определить очистку кеша при смене метода/профиля.
- Проверить доступ к сертификатам и закрытым ключам от LocalSystem, способы выбора
  клиентского сертификата и возможность машинной аутентификации.
- Для L2TP/IPsec проверить PSK в собственной телефонной книге и необходимые условия NAT-T.
  Не менять глобальные параметры NAT-T на рабочей машине автоматически.
- Зафиксировать окончательную матрицу «протокол × вход × требуемые данные» и ограничения.

**Готово:** технический отчёт с фактическими результатами, точными API и схемами EAP;
неразрешённые вопросы сертификатов/TTLS явно вынесены до основной реализации.

### 2. Модель настроек и безопасная совместимость

- Добавить независимые настройки протокола, пользовательской аутентификации,
  способа проверки IPsec и параметров доверия сертификатам.
- Валидировать сочетания централизованно в ядре и повторно на стороне службы.
- Порт разрешать только для SSTP; другие RAS-протоколы принимают имя сервера/IPv4 без порта.
- Ввести новую версию схемы: старые профили мигрируют в SSTP + MS-CHAPv2 без изменения поведения.
  Старая служба должна отвергать новую схему, а не проигнорировать протокол и подключить SSTP.
- Проверять совместимость версий UI/IPC/службы; неизвестные методы отвергать явно.
- Импорт/экспорт переносит настройки доверия и ссылки на сертификаты, но не пароли,
  PSK или закрытые ключи. После импорта проверять доступность сертификата на этом ПК.

**Готово:** тесты миграции, неизвестных значений, недопустимых сочетаний и экспорта без секретов.

### 3. Секреты, сертификаты и EAP

- Разделить хранение пароля и PSK по профилю; PSK сохранять через DPAPI и существующие ACL.
  Параметр «Сохранять пароль» управляет пользовательским паролем; хранение PSK явно описать в UI.
- Отдельные IPC-команды для записи/очистки PSK, с маскированием ToString и запретом журналирования.
- Удалять ненужные секреты при удалении профиля и смене способа входа/IPsec; очищать временные буферы.
- Формировать EAP XML из типизированных параметров, преобразовывать через EAPHost,
  записывать конфигурацию средствами RAS. Не хранить учётные данные внутри XML профиля.
- Для сертификатов проверять срок, назначение, цепочку доверия и доступность закрытого ключа службе.
  В профиле хранить только идентификатор сертификата/критерии выбора и настройки доверия.
- Не отключать проверку сертификатов для обхода ошибок. Установка сертификатов и выдача прав
  на закрытые ключи должны быть отдельными явными действиями пользователя.

**Готово:** отрицательные тесты отсутствующих/недоступных секретов и сертификатов;
проверено отсутствие секретов в JSON, IPC-ответах, журналах и диагностическом экспорте.

### 4. Дозвон и жизненный цикл службы

- Передавать в RAS полное описание подключения вместо одной строки сервера.
- Настраивать конкретный miniport, VPN strategy, флаги входа, EAP и PSK/сертификат.
- Читать проекцию PPP или IKEv2 по возвращённому типу.
- Учитывать протокол, вход и сертификаты в сравнении применённых параметров.
- Обработать изменения во время дозвона: устаревший результат не должен подхватиться как новый профиль.
- При подхвате после перезапуска проверять соответствие соединения текущему профилю.
- Обновить пробный дозвон, повторные попытки и ошибки PSK/IKE/EAP/сертификатов.
- Различать «нужен пароль», «нужен ключ IPsec», «нужен сертификат»; не требовать пароль для EAP-TLS.

**Готово:** тесты координатора на смену протокола при том же сервере, смену метода/секрета,
перезапуск службы, пробное соединение и конкурентное изменение профиля во время дозвона.

### 5. Защита трафика и маршруты

- SSTP: TCP к выбранному порту; PPTP: TCP 1723 и GRE (IP 47).
- L2TP/IPsec: IKE UDP 500, NAT-T UDP 4500, ESP (IP 50), L2TP UDP 1701.
- IKEv2: UDP 500/4500 и ESP; L2TP-порт не разрешать.
- Все исключения ограничить адресами выбранного сервера и основным адаптером.
- На стенде проверить взаимодействие ALE-фильтров с IPsec и GRE: перечня разрешённых портов
  недостаточно, чтобы утверждать работоспособность. Для UDP 1701 проверить отсутствие
  незащищённой передачи L2TP и применимость ограничения по IPsec-состоянию/слою WFP.
- Сохранять приоритет пользовательских блокировок, DNS-стража и правил при обрыве.
- Проверить атомарную смену фильтров при смене протокола; удаление старых разрешений,
  маршруты к серверу и восстановление после перезапуска.

**Готово:** модульная матрица разрешений/запретов плюс сетевой захват на стенде
при подключении, обрыве и переподключении для каждого транспорта.

### 6. Интерфейс и документация

- В редакторе и мастере: выбор протокола, только совместимые способы входа,
  условные поля логина/пароля, PSK, сертификатов, CA и имён сервера аутентификации.
- Показывать протокол и способ входа в списке профилей и диагностике.
- Очищать несохранённые секреты при переключении профиля; явно различать «не менять» и «удалить».
- При изменении протокола сообщать, какие несовместимые параметры будут сброшены;
  не заменять выбранный способ входа молча.
- Обновить руководство по сертификатам, ограничения, примеры профилей и восстановление сети.

**Готово:** проверены все ветки мастера/редактора, импорт/экспорт, клавиатурная навигация,
отображение ошибок и отсутствие пароля в сертификатных сценариях.

### 7. Приёмка и выпуск

- Release-сборка без предупреждений; тесты ядра, службы и Windows-обёрток.
- Регрессия текущего SSTP + MS-CHAPv2, миграции настроек, DNS и разделения трафика.
- На тестовых серверах: хотя бы одно успешное соединение на каждый протокол и каждый
  заявленный способ входа; проверка ключевых допустимых сочетаний матрицы.
- Негативные сценарии: неверный пароль/PSK, недоверенный и просроченный сертификат,
  неверное имя сервера, недоступный закрытый ключ, сервер с несовместимым методом.
- Проверка обрыва, сна/возобновления, перезапуска службы и возврата обычного интернета.
- Затем сборка установщика и проверка обновления/отката с новой схемой настроек.
  Установку на рабочий ПК планировать отдельным шагом после проверок.

**Готово:** отчёт разделяет модульные тесты, локальные проверки API и реальные соединения.
Отсутствующий сервер — ограничение приёмки, а не основание объявлять метод проверенным.

## Что потребуется для сетевой приёмки

Тестовые серверы/учётные записи L2TP/IPsec, IKEv2, PPTP и серверы с EAP/PEAP/TTLS,
а также тестовые сертификаты для EAP-TLS и машинного IPsec. Наличие старых профилей
Windows само по себе не подтверждает доступность серверов и не разрешает читать их секреты.
Планирование и модульная разработка после согласования не зависят от предоставления этих данных.

## Состояние до согласования

После требования сначала планировать изменения кода прекращены. На этапе 2 черновик

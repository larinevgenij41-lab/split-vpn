# План: отзывчивость службы

Статус: анализ 2026-09-14, к работе не принят. Исходная жалоба — интерфейс показывает «Служба не отвечает», команды выполняются с задержкой.

## Что уже сделано (0.3.9, коммит 0b3a33d)

- Группа WFP `[Direct]` (≈19,6 тыс. фильтров прямых диапазонов RU-базы) обновляется разницей, а не заменяется целиком: сверка после входа в AnyConnect — 2 с вместо 12–13 с.
- Запрос состояния получает последний снимок, если очередь занята дольше 0,5 с.
- В журнал пишется «Сверка заняла N мс: этапы» для `ApplyAsync` дольше 1 с.

## Почему «Служба не отвечает» ещё возможна

1. Порог 0,5 с проверяется один раз при входе запроса: запрос, пришедший в начале долгой работы, между работами или во время `StartupAsync` (снимка ещё нет), ждёт всю очередь.
2. Мимо очереди идёт только состояние: журнал, настройки, адаптеры, отчёт ждут очередь с таймаутом 5 с.
3. Клиент (`App\Services\ServiceConnection.cs`) держит одно соединение и семафор без таймаута: пока команда идёт до 60 с, опрос состояния стоит у клиента. Проверка версии при переподключении — таймаут 2 с.

## Долгие работы в очереди актора

| Где | Длительность | Частота |
|---|---|---|
| WFP `ReplaceGroup` — по вызову на фильтр; первая установка Direct | 5–12 с | запуск, смена базы или правил |
| `WfpOps.ListFilters` — перебор всех фильтров BFE без шаблона | 0,3–1,5 с | каждое изменение группы; `InstalledCounts` раз в 60 с |
| Доменные правила: каждый новый адрес → политика, WFP Dynamic, маршруты, без объединения | 0,5–2 с на адрес | лавина при открытии сайта |
| `FilterFingerprint` по 19,6 тыс. строкам | 50–200 мс | 1–2 раза за сверку |
| `RouteOps.Reconcile` — первая установка тысяч маршрутов | секунды | изменения, раз в 60 с |
| `NetInventory.Capture` | 50–200 мс | каждые 2 с и несколько раз за сверку |
| `RasHangUp` + ожидание до 15 с | 1–15 с | отключение, смена данных, подхват |
| `VerifyAsync` — две TCP-пробы по 5 с | до 10 с | после поднятия туннеля |
| Разрешение сервера и шлюза AnyConnect — 3 с на каждый DNS-сервер | до 3·N с | пустой кеш, раз в час, `ResolveHost` |
| `ipconfig /flushdns` запуском процесса | 0,1–0,5 с | каждая смена конфигурации посредника |
| «Проверить адрес» — системный резолвер без таймаута | до 10+ с | по запросу |
| `ConflictDetector` (RAS, маршруты, все фильтры WFP) | 0,5–2 с | раз в 5 мин |
| Причина обрыва RAS из журнала событий | до 3 с | при обрыве |
| `VpnCertificates.Validate` — проверка отзыва онлайн | до 5+ с | дозвон с EAP-TLS |
| Полная сверка в каждом обработчике события и команды, без объединения | сверка | каждое событие |

Риск: исключение не из перехваченных типов в `TickAsync` или обработчике помощника выходит из цикла актора и останавливает службу.

## Выводы

- Единый актор оправдан: системные изменения должны идти упорядоченно и fail-closed, состояние изменяемое. Последовательными остаются решения и применение WFP, маршрутов, DNS, RAS.
- `async/await` («корутины») освобождает поток, но не очередь: цикл ждёт `await work()`. Синхронные API (WFP, IP Helper, RAS, запуск процессов) блокируют и поток. Помогают: не держать очередь во время ожидания (начать → событие с результатом и поколением), не делать лишнюю работу (объединение сверок, инкрементальность), не пропускать чтения через очередь.

## План по приоритету

1. **Замеры** (полдня, первым): время ожидания и выполнения каждого элемента очереди с типом, глубина очереди; предупреждение > 500 мс; разбивка для `TeardownAsync`, `EnsureRoutesSafe`, тика; WFP и маршруты — перечислено/удалено/добавлено/время; максимум и p95 в отчёте.
2. **Чтение без очереди** (< 1 дня, низкий риск): состояние ждёт очередь не больше 250 мс, затем снимок; снимок до `StartupAsync` и после её этапов; журнал, настройки, адаптеры напрямую; у клиента — отдельное соединение для опроса или таймаут на семафоре.
3. **Объединение** (1–2 дня): сверка по флагу после выборки очереди; адреса DNS-посредника пачкой раз в 100–200 мс только в маршруты и Dynamic; `Stats`/`Log` помощника без очереди.
4. **Удешевление WFP** (1–2 дня): ID фильтров по группам в памяти, перебор BFE с шаблоном провайдера только для контроля дрейфа, отпечаток Direct по входным данным.
5. **Долгие ожидания в фон с поколением** (2–3 дня): `HangUp`, `VerifyAsync`, разрешение имён, `ConflictDetector`, причина обрыва, проверка сертификата; `FlushCache` через `DnsFlushResolverCache`.
6. **Сеть без опроса каждые 2 с** (1 день): `NotifyIpInterfaceChange`/`NotifyUnicastIpAddressChange` плюс контрольный `Capture` раз в 30–60 с.
7. По итогам замеров, если понадобится: отдельный исполнитель желаемого состояния.

Тесты — `tests\SplitVpn.Service.Tests` (`Fakes.cs`): «ворота» в фейках для долгой работы, счётчики вызовов `ReplaceGroup`/`Reconcile`/`Capture`, игнорирование устаревших результатов по поколению.
